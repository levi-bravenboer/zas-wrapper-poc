## Context

`apps/digital-front-door` is the new patient-facing mobile surface, scaffolded as an Expo SDK 54 app. The PoC currently ships a single web app (`apps/orchestrator`, shadcn + Tailwind). We want the patient app to feel like a deliberate sibling of the orchestrator — same component-design vocabulary, same Tailwind utility classes where they translate, same module layout — without binding to the orchestrator's web-only primitives.

This change covers the **shell only**: project init, design-system foundation, routing, data layer, i18n, lint, typecheck, tests, moon wiring. No clinical features, no Luscii embed, no patient auth.

The stack picks below were chosen in order so each decision constrains the next.

## Goals / Non-Goals

**Goals:**
- One installable Expo app on iOS, Android, and web.
- Tailwind-first styling. No `StyleSheet`, no inline style objects.
- Headless accessibility primitives wrapped in our own design system at `src/components/ui/*`.
- Folder layout that mirrors `apps/orchestrator` so a contributor moving between apps sees the same shapes.
- Same data + i18n primitives as orchestrator (TanStack Query, generated OpenAPI client, `i18next`).
- Moon tasks pre-approved; no permission prompts for routine commands.
- MDR-safe scaffold: no clinical logic, no measurements, no decision support.

**Non-Goals:**
- Patient login or auth flows (separate change).
- Patient pathway view, task view, Luscii deep-link (separate changes).
- EAS build / submit configuration, OTA updates, store metadata.
- Push notifications, deep linking strategy beyond expo-router defaults.
- Real device CI matrix; PoC stays on simulator + web preview.
- Backend changes; patient-facing endpoints are MVP-tier.

## Decisions

### D1 — Package manager: **pnpm**

Self-contained pnpm per app (own `pnpm-lock.yaml` in `apps/digital-front-door/`). Matches `apps/orchestrator` pattern. No root `pnpm-workspace.yaml`; apps stay independent so Metro doesn't have to traverse the orchestrator graph.

**Why:** Consistency with orchestrator; pnpm is the only JS package manager already in the repo; SDK 54 officially supports pnpm.

**Alternatives considered:**
- npm / yarn classic: drift from orchestrator.
- bun: faster, but less monorepo-tested with Metro; not used elsewhere in repo.
- Root pnpm workspace: would pull orchestrator deps into the mobile resolution graph for no benefit at PoC scale.

**Compat note:** `.npmrc` with `node-linker=hoisted` (auto-generated by `create-expo-app`) is kept until SDK 54's isolated-deps mode is proven against `expo-router` 6 in our setup.

### D2 — Expo SDK: **56.0.x** (newest stable, adopted from `create-expo-app@latest`)

Stack pinned by SDK 56:

| Knob | SDK 56 |
|---|---|
| `expo` | `~56.0.8` |
| `react` | `19.2.3` |
| `react-native` | `0.85` |
| `react-native-web` | `0.21.0` |
| `expo-router` | `~56.x` (unified package versioning — SDK major == package major from SDK 56) |
| `react-native-reanimated` | `4.3.1` (rewritten for the New Architecture) |
| `react-native-worklets` | bundled separately and tightly coupled to Reanimated 4 |
| iOS minimum | **16.4+** (was 15.1 on SDK 55 — drops iPhone 6s / 7 / 8) |
| Xcode | 26.4+ |
| Android | 7+ (unchanged) |
| Node | **22.13.x** (was 20.19 on SDK 55) |

**Why bump 55 → 56.** `create-expo-app@latest` shipped SDK 56 once we ran the scaffold; we accepted the newer version on the user's standing preference ("newest stable"). SDK 56 is stable per `docs.expo.dev/versions/v56.0.0`. The PoC has no real users yet, no published builds, no real-device dependency matrix — drift from gosta's SDK 55 baseline carries no real cost at this stage.

**Risks introduced by the bump.**
- **iOS 16.4 deployment target.** Drops iPhone 6s/7/8 + early iPads from the supported list. Healthcare patient demographics include older devices; verify with the hospital before any pilot. PoC demo is simulator-only → no risk now.
- **Node 22.13 minimum.** Root `.moon/toolchain.yml` is on Node 20.19 today. The toolchain bump is part of this change (see task list).
- **Reanimated 4 + `react-native-worklets`** are the new world. `babel-preset-expo` auto-configures both; **no manual `react-native-reanimated/plugin` entry in `babel.config.js`**. This deviates from older guides that say to add it manually.
- **`expo-router ~56.x`** instead of `~6.x` — community examples may still cite `expo-router@6`; mentally translate.
- Ecosystem is fresh — `react-native-keyboard-controller` and other community libs were verified against Reanimated 3 first. Reanimated 4 backward-compat is documented but not battle-tested in our exact combo.

### D3 — Styling: **NativeWind v4**

All visual styling is expressed as Tailwind utility classes on the `className` prop. No `StyleSheet`, no inline `style={{ … }}` objects in product code (RN-specific style overrides for animated values or measured layout are the only exception, and live behind a clear comment).

**Why:** Direct vocabulary parity with `apps/orchestrator`. Same Tailwind config patterns translate. NativeWind v4 ships first-class Expo SDK 54 + Metro integration.

**Alternatives considered:**
- Plain `StyleSheet` + theme object: zero deps, but loses Tailwind DX and the shared mental model with orchestrator.
- Tamagui: best perf at scale, but its own styling engine conflicts with the Tailwind-only rule.
- Unistyles 3: RN-native, fast, but not Tailwind.
- Restyle: typed style props, theme-driven, but again non-Tailwind.

### D4 — Component primitives: **`@rn-primitives/*`** + our own wrappers

Use the headless `@rn-primitives/*` family (Radix-style accessibility primitives ported to RN) for any compound component that needs state, focus management, or a11y semantics: `accordion`, `alert-dialog`, `aspect-ratio`, `avatar`, `checkbox`, `collapsible`, `context-menu`, `dialog`, `dropdown-menu`, `hover-card`, `label`, `menubar`, `navigation-menu`, `popover`, `portal`, `progress`, `radio-group`, `scroll-area`, `select`, `separator`, `slider`, `slot`, `switch`, `tabs`, `toggle`, `toggle-group`, `tooltip`.

Wrap each one in `src/components/ui/<name>.tsx`. Wrappers expose a styled component with `class-variance-authority` (`cva`) variants and a `cn()` helper, matching the orchestrator's shadcn pattern. For RN core primitives (`Pressable`, `TextInput`, `View`, `Text`, `ScrollView`, `FlatList`), wrap directly — no extra dependency.

Icons: **`lucide-react-native`** (className-aware via NativeWind).

**Why:** Maximum coverage of accessible compound components with zero opinion on visuals. We own the design system; the library owns a11y + interaction logic.

**Alternatives considered:**
- `react-native-reusables` (rnr): pre-styled shadcn ports of the same primitives. Useful starter, but pre-styled wrappers mean we'd either delete and rewrite styling or fight defaults. Skipped.
- Gluestack UI v2: larger catalog, NativeWind-compatible, but its theme system competes with Tailwind utilities.
- Tamagui UI: would re-open D3.
- Roll-everything: slow, no a11y wins.

### D5 — Wrapper convention

```tsx
// src/components/ui/button.tsx
import { Pressable, type PressableProps } from 'react-native';
import { Text } from 'react-native';
import { cva, type VariantProps } from 'class-variance-authority';
import { cn } from '@/lib/cn';

const buttonVariants = cva(
  'flex-row items-center justify-center rounded-md px-4 py-2',
  {
    variants: {
      variant: {
        default: 'bg-primary',
        secondary: 'bg-secondary',
        ghost: 'bg-transparent',
      },
      size: { sm: 'h-8', md: 'h-10', lg: 'h-12' },
    },
    defaultVariants: { variant: 'default', size: 'md' },
  }
);

export type ButtonProps = PressableProps & VariantProps<typeof buttonVariants>;

export function Button({ className, variant, size, ...props }: ButtonProps) {
  return <Pressable className={cn(buttonVariants({ variant, size }), className)} {...props} />;
}
```

`cn()` lives at `src/lib/cn.ts` (`twMerge(clsx(...))`), identical signature to orchestrator's.

### D6 — Routing: **expo-router v6** with grouped auth/app shells

File-based routing. Top-level groups separate authenticated and unauthenticated surfaces:

```
app/
  _layout.tsx              # Root provider stack: QueryClient, i18n, NativeWind ThemeProvider, SafeAreaProvider
  (auth)/
    _layout.tsx            # Stack; redirects to (app) when session present
    login.tsx              # Placeholder screen (real flow lands in patient-auth change)
  (app)/
    _layout.tsx            # Tabs or stack; redirects to (auth)/login when session absent
    index.tsx              # Patient home placeholder
  +not-found.tsx
```

Auth state in PoC = `null` until the patient-auth change lands; root layout currently sends every visitor to `(auth)/login`. The `(auth)` / `(app)` split lives in the scaffold so feature changes plug into a stable shape.

**Web target**: kept enabled as a dev convenience (faster reload than simulator, easier screenshots for review). Not a shipping channel — delivery-channel decision still parked in `BL-014`. `app.json` keeps `web: { bundler: "metro" }`.

**Why grouped from day one:** unauth/auth shape is universal in patient apps; retrofitting `(auth)`/`(app)` after screens land means renaming every route file.

**Alternatives considered:**
- Flat routes: simpler now, painful later.
- File-system + manual `<Stack>` config: more flexible, but loses expo-router's typed routes (`expo-router/typed-routes`) and link generation.

### D7 — Data layer: **TanStack Query v5**, no OpenAPI client yet

`@tanstack/react-query` v5 owns server state. `QueryClient` instantiated once in `src/lib/queryClient.ts`; `QueryClientProvider` mounted in `app/_layout.tsx`.

Transport: a thin `src/lib/api.ts` placeholder exporting a configured `fetch` wrapper with base URL from `expo-constants` (`extra.apiBaseUrl`) and JSON encode/decode. No interceptor stack until the auth change adds session headers.

**No generated OpenAPI client in this change.** The backend exposes no patient-tier routes yet. Wiring `openapi-typescript` against a non-existent surface generates noise. The first patient feature change adds the codegen step and pre-approves a `moon run digital-front-door:typegen` task mirroring `orchestrator:typegen`.

Query key convention matches orchestrator: `['fhir', ResourceType, id]` style once endpoints exist; placeholders use plain strings.

**Why:** TanStack Query is the orchestrator's data primitive; carrying it forward keeps mental model identical. Deferring codegen avoids dead types.

**Alternatives considered:**
- RTK Query: not used elsewhere in repo.
- SWR: lighter, but no orchestrator parity.
- Hand-rolled hooks over `fetch`: misses cache, invalidation, retry.

### D8 — i18n: **`i18next` + `react-i18next`**, Dutch-only at scaffold

Same primitives as orchestrator. Configured at `src/lib/i18n/index.ts` and initialised in `app/_layout.tsx` before any UI mounts.

- **Locales shipped**: `nl-BE` only.
- **Default locale**: `nl-BE`.
- **Fallback locale**: `nl-BE` (same — no English bundle at scaffold).
- **Resource layout**: per-feature locale files, namespaced. Scaffold ships `src/lib/i18n/locales/nl-BE/common.json` (skeleton with a couple of keys used by the placeholder screens).
- **Loader**: bundled JSON imports for PoC. Remote/async loaders are a later concern.
- **No raw Dutch strings in product code.** Every user-visible string MUST flow through `t(...)`. Source keys are English (`auth.login.title`); values are Dutch (`Aanmelden`). Matches the code-identifiers-English / Dutch-only-in-translations memory rule.
- **Language detection**: off. Device locale is ignored at scaffold; the app is unconditionally `nl-BE`. When English (or any second locale) is needed, a separate change wires `expo-localization` + the i18n detector.

**Why:** Orchestrator parity. Lets future translations land without restructuring code. Forces discipline (no hardcoded Dutch in JSX) from day one.

**Alternatives considered:**
- LinguiJS: more compile-time tooling, but new dependency family for the repo.
- Format.JS / `react-intl`: heavier API; orchestrator already standardised on `i18next`.
- Skip i18n until a second locale is needed: cheap now, expensive later (every Dutch string becomes a refactor).

### D9 — React Native New Architecture: **enabled**

Fabric + TurboModules + bridgeless mode. Default for any project created with `create-expo-app@latest` from SDK 52 onward; we keep it on. Means no `bridge` deprecation noise, faster startup, fewer surprises in 2026.

**Mitigation:** any third-party native dep added later must be New-Arch-compatible; the pinned `@rn-primitives/*` family and `expo-router` 6 already are.

### D10 — Typed routes: **enabled**

`expo.experiments.typedRoutes: true` in `app.config.ts`. Generates `.expo/types/router.d.ts` so `<Link href="/...">` and `router.push(...)` are typed against the actual file tree.

**Why:** Catches stale links at compile time. The grouped `(auth)` / `(app)` shells make typed routes especially valuable — renames across groups otherwise propagate silently.

### D11 — App config: **`app.config.ts`** (TypeScript)

Use `app.config.ts` from day one instead of `app.json`. Imports `ExpoConfig` and `ConfigContext` from `expo/config` for type safety. Keeps env-driven config (`process.env.EAS_BUILD_PROFILE`, future API base URL injection) ergonomic.

```ts
import type { ConfigContext, ExpoConfig } from 'expo/config';

export default ({ config }: ConfigContext): ExpoConfig => ({
  ...config,
  name: 'Digitale voordeur',
  slug: 'digital-front-door',
  scheme: 'digitale-voordeur',
  userInterfaceStyle: 'light',
  ios: { bundleIdentifier: 'com.reaktor.zas.digitalfrontdoor', supportsTablet: true },
  android: { package: 'com.reaktor.zas.digitalfrontdoor' },
  web: { bundler: 'metro' },
  experiments: { typedRoutes: true, reactCompiler: true },
  extra: { apiBaseUrl: process.env.EXPO_PUBLIC_API_BASE_URL ?? null },
});
```

### D12 — React Compiler: **enabled**

React 19.1 + the React Compiler Babel plugin (`babel-plugin-react-compiler`) auto-memoize components and hooks. Activate via `expo.experiments.reactCompiler: true` (SDK 54 wires the plugin automatically — no separate install).

**Why:** Removes most hand-rolled `useMemo` / `useCallback` / `React.memo` from product code. Aligns with 2026 React best practice.

**Trade-off:** Adds Babel build time. Acceptable at scaffold scale. If a component is known-incompatible, opt out per-file via the `'use no memo'` directive at the top of the file.

```

      _layout.tsx              # Root: QueryClient, i18n, SafeArea, status bar
      (auth)/
        _layout.tsx
        login.tsx              # placeholder (real flow = later change)
      (app)/
        _layout.tsx
        index.tsx              # patient home placeholder
      +not-found.tsx
    components/
      ui/                      # wrappers over @rn-primitives + RN core; Tailwind-styled
    modules/                   # vertical feature modules (orchestrator parity)
      <domain>/

          use-update-foo.ts    # wraps useMutation(fooMutations.update())
        components/
          <kebab-case>.tsx
    providers/                 # cross-cutting context providers
    hooks/                     # cross-cutting hooks
    lib/
      cn.ts
      api.ts                   # placeholder fetch wrapper
      queryClient.ts

  assets/
  app.config.ts                # NOT app.json
  babel.config.js
  metro.config.js
```

**Why `src/app/` and `src/modules/`:** expo-router officially recognizes `app/` at root OR `src/app/`. The `src/app/` shape lets every non-route file sit under `src/`, mirroring orchestrator. `src/modules/<domain>/` matches orchestrator's `src/modules/<domain>/` exactly so caregiver-app and patient-app contributors see the same vocabulary.

### D14 — Lint + format: **Prettier + ESLint flat config** (diverges from orchestrator's Biome)

Mobile uses **Prettier** for formatting and **ESLint** (flat config) for static checks. This intentionally diverges from `apps/orchestrator`'s Biome setup.

**Why diverge:** Biome's formatter does not sort Tailwind class names. NativeWind makes Tailwind classes load-bearing in every JSX file; unsorted classes generate noisy diffs and obscure visual intent. `prettier-plugin-tailwindcss` solves this cleanly. Orchestrator parity loses to mobile pragmatism here.

**Prettier config** (`.prettierrc`):
- no semicolons
- single quotes
- trailing comma `es5`
- `printWidth: 80`
- 2-space indent
- `arrowParens: 'always'`
- plugin: `prettier-plugin-tailwindcss` for class-name sorting

**ESLint config** (`eslint.config.js`, flat) — base `eslint-config-expo/flat`. Adopted rules (drawn from a sibling Expo project after a head-to-head best-practice review):

Tier 1 — file / import / type / logging hygiene:
- `eslint-plugin-simple-import-sort` — five-tier order: node/built-ins → external → `@/...` → `./` → side-effects+styles.
- `eslint-plugin-check-file` `filename-naming-convention` — kebab-case everywhere.
- `@typescript-eslint/no-explicit-any: error` — no `any`.
- `@typescript-eslint/no-non-null-assertion: error` — no `!`.
- `@typescript-eslint/consistent-type-imports: error` — inline `import type {...}`.
- `@typescript-eslint/consistent-type-definitions: ['error', 'type']` — `type` over `interface` for non-component shapes; component props stay `interface XProps`.
- `@typescript-eslint/consistent-type-assertions: ['error', { assertionStyle: 'never' }]` — no `as Foo` casts. **Exempted in `__tests__/`** where partial-mock helpers are unavoidable.
- `@typescript-eslint/use-unknown-in-catch-callback-variable: error` — typed `catch` bodies.
- `@typescript-eslint/prefer-nullish-coalescing: error`.
- `@typescript-eslint/promise-function-async: error`.
- `@typescript-eslint/no-restricted-types: error` — ban `Function`, `{}`, `Object`.
- `no-console: ['error', { allow: [] }]` — force `@/lib/logger` (`log.info|warn|error`). `lib/logger.ts` itself exempted.
- `no-restricted-syntax`:
  - `TSEnumDeclaration` — banned. Use string union + `as const`.
  - `CallExpression[callee.name='forwardRef']` and `CallExpression[callee.object.name='React'][callee.property.name='forwardRef']` — banned. React 19 ref-as-prop.
- `no-restricted-imports` — block `../*`, force `@/...` for cross-folder.
- `i18next/no-literal-string: error` — no Dutch literal in JSX or props; every string flows through `t()`.
- `import/no-default-export: error` — except in route files (`src/app/**`) and config files (`*.config.{js,ts,mjs,cjs}`, `app.config.ts`).
- `react/function-component-definition: ['error', { namedComponents: 'function-declaration' }]` — `export default function Foo(...)`. No arrow components.

Tier 2 — TanStack discipline:
- `@tanstack/query/exhaustive-deps: error`.
- `no-restricted-syntax` for `CallExpression[callee.name=/^useQuery$|^useMutation$/]` inside `src/app/**` and `src/components/ui/**` — raw `useQuery`/`useMutation` calls must go through `src/modules/<x>/hooks/use-*.ts`.

Rollout: ship as warnings initially in the scaffold (no existing code to violate); flip to errors at the bottom of the same change once the empty scaffold is green.

Moon wiring: `digital-front-door:lint` (eslint), `digital-front-door:format` (prettier --write), `digital-front-door:format-check` (prettier --check). Pre-approved in `CLAUDE.md`.

### D14b — Design tokens: **independent from orchestrator**

`apps/digital-front-door/tailwind.config.js` is hand-rolled. No copy, no import, no shared `packages/design-tokens` preset. The mobile app owns its own palette, typography scale, spacing, and radii.

**Why:** Patient-facing mobile UI and caregiver-facing desktop UI serve different audiences and platforms (touch vs pointer, smaller viewport, OS-native conventions). Forced visual parity with orchestrator would constrain the mobile design language without product benefit. Visual divergence is **accepted by intent**, not a defect to be reconciled.

**Trade-off:** Two truth-of-tokens to maintain. Mitigated by the fact that orchestrator and this app have different design languages — there is no "single brand token set" we are trying to keep in sync.

**Out of scope:** if/when a shared brand emerges, a later change can extract `packages/design-tokens` and migrate both apps. Not preempted here.

### D15 — Tests: `jest-expo` + mirror tree + fixtures + provider helper

Use `jest-expo` preset. Component tests via `@testing-library/react-native`. Router tests via `expo-router/testing-library` `renderRouter`. No e2e in this scaffold; Maestro / Detox is a later decision.

**Why not vitest:** orchestrator uses vitest because Vite ecosystem. Expo's first-class runner is jest. Forcing vitest here means hand-rolling Metro/Babel parity.

**Test layout** mirrors the source tree under `__tests__/`:

```
__tests__/
  app/                          screen integration tests
  components/ui/
  modules/<x>/
    components/
    hooks/
    api.test.ts
    utils.test.ts
  lib/
  fixtures/<x>.ts               shared mock factories (makeFoo(overrides?: Partial<Foo>))
  utils/
    render-with-providers.tsx   wraps QueryClientProvider (+ later, Jotai store)
```

**Render helper** (`__tests__/utils/render-with-providers.tsx`):

```tsx
export const renderWithProviders = (ui: ReactElement) => {
  const qc = new QueryClient({
    defaultOptions: { queries: { retry: false, gcTime: 0 } },
  });
  return render(<QueryClientProvider client={qc}>{ui}</QueryClientProvider>);
};
```

**Fixture pattern**: each domain exposes `make<Entity>(overrides?: Partial<Entity>): Entity`. No inline literal mock objects in test bodies.

**Coverage**: collected but no thresholds enforced in this change.

**Default mocks** (configured in `jest.setup.ts`):
- `expo-secure-store` → in-memory.
- Network fetcher → mocked at module level; never hit real network.
- `react-native-localize` → fixed `nl-BE`.
- TanStack Query client → real, retry off, gcTime 0.

### D18 — Backend route prefix + first endpoint: **`/mobile/*`** with `GET /mobile/health`

Every backend route consumed by `digital-front-door` lives under the **`/mobile/`** prefix. The prefix names the consumer surface (the mobile app), not the audience (patient). This lets us:

- attach a single CORS rule + auth middleware family to all mobile-app traffic at one place;
- introduce a patient-session middleware later without renaming existing routes;
- enforce an MDR boundary at the prefix once feature work begins.

**First endpoint shipped with this scaffold** (small exception to "no backend changes" in proposal Impact):

- `apps/backend/app/api/routers/mobile/__init__.py`
- `apps/backend/app/api/routers/mobile/health_router.py`:
  ```python
  from fastapi import APIRouter
  router = APIRouter(prefix="/mobile", tags=["mobile"])

  @router.get("/health")
  def health() -> dict[str, str]:
      return {"status": "ok"}
  ```
- Registered in `apps/backend/app/api/__init__.py` alongside the other resource routers.
- OpenAPI regenerated via `/openapi-sync` so the orchestrator client never drifts.

**Mobile-side use:**

- `EXPO_PUBLIC_API_BASE_URL` points at the backend root (e.g. `http://localhost:8000`); the path `/mobile/health` is appended by `src/lib/api.ts`.
- `src/lib/api.ts` exports `apiHealthCheck()` — a typed `fetch` call returning the parsed `{ status: 'ok' }` shape.
- `src/app/_layout.tsx` fires `apiHealthCheck()` exactly once on first mount and logs the result. **No UI.** The check is a connectivity smoke test, not a user-visible probe.

**Why a health endpoint now, when proposal Impact said "no backend changes":** the user's intent for the scaffold is "good base to start building the actual app." A round-trip from device to backend, with the prefix wired and an OpenAPI entry present, validates the wiring before the first real feature change has to fight it. Proposal Impact section updated to reflect this.

**Trade-off:** the prefix names the platform (mobile), not the audience (patient). If a future desktop patient app appears, this naming is wrong. Accepted today; revisit at audience-prefix introduction (recorded as an open question).

### D19 — Filename + export naming convention

All filenames **kebab-case**. Exports follow their kind:

| Item | Filename | Export |
|---|---|---|
| Component | `kebab-case.tsx` (`button.tsx`, `side-menu.tsx`) | `PascalCase` via `export default function Button() {}` |
| Hook | `kebab-case.ts(x)` (`use-foo.ts`, `use-update-foo.ts`) | `useCamelCase` |
| Service / lib module | `kebab-case.ts` (`api-base.ts`, `cn.ts`) | `camelCase` fns + `PascalCase` types |
| Test | source name + `.test.ts(x)` | — |
| Native split | `*.native.ts(x)` | — |
| Route file | `kebab-case.tsx` (`+not-found.tsx`, `login.tsx`) | route default export |
| Route group | `(lowercase)/` (`(auth)/`, `(app)/`) | — |
| Dynamic route | `[param].tsx` | — |
| Folder | lowercase + kebab if multi-word | — |
| Type / interface | — | `PascalCase` (`UserAuthInformation`, `ButtonProps`) |
| Constant | — | `SCREAMING_SNAKE_CASE` |

Enforced via `check-file/filename-naming-convention`.

### D20 — Module hygiene + cross-folder imports

- Every `src/modules/<x>/` exposes a barrel `index.ts` that re-exports `atoms`, `types`, `api`, `queries`, `mutations` (omit when absent).
- Cross-folder imports MUST use the `@/...` alias. Same-folder imports use relative `./`.
- Cross-module reads MUST go through the module barrel (`@/modules/auth`), never through internals (`@/modules/auth/atoms`). Enforced by `no-restricted-imports`.
- `src/components/ui/` is domain-free: no API calls, no module imports, no module-specific i18n keys.
- `src/lib/` is feature-free: no domain types, no module imports.
- `src/app/` is routing-only: layouts + thin screens composing module components/hooks. No business logic in route files.

### D21 — Data layer pattern: `queryOptions` factory + always-via-hook

Per-module structure:

```ts
// src/modules/<x>/queries.ts
import { queryOptions } from '@tanstack/react-query';
import { getFoo, listFoos } from './api';

export const fooQueries = {
  all: () => ['foo'] as const,
  detail: (id: string) =>
    queryOptions({
      queryKey: [...fooQueries.all(), 'detail', id],
      queryFn: () => getFoo(id),
    }),
  list: () =>
    queryOptions({
      queryKey: [...fooQueries.all(), 'list'],
      queryFn: () => listFoos(),
    }),
};

// src/modules/<x>/hooks/use-foo.ts
export const useFoo = (id: string) => useQuery(fooQueries.detail(id));
```

**Rules:**
- One key factory per module.
- Components and screens NEVER call `useQuery` / `useMutation` inline. Always wrap as `use-*.ts`. Enforced by ESLint `no-restricted-syntax` in `src/app/**` and `src/components/ui/**`.
- Cascade invalidate via `fooQueries.all()`; never hand-build invalidation keys.
- `api.ts` exports pure fetch fns. No TanStack imports in `api.ts`.

### D22 — Client state library: **Jotai** (installed at scaffold, no atoms shipped)

Server state lives in TanStack Query. UI / session-mirror state lives in **Jotai** atoms.

The library is installed in this change so the first feature change can `import { atom } from 'jotai'` without re-debating the choice. **No atoms are defined in this change** — there is no UI to back. `src/providers/jotai.tsx` is a thin wrapper that re-exports `Provider` from `jotai` and is mounted in `src/app/_layout.tsx`; the default store is used.

**Convention** (recorded for future feature changes):
- Atoms live per module at `src/modules/<x>/atoms.ts`.
- Server data never lives in atoms.
- Auth tokens never live in plain atoms — they live in `expo-secure-store` (D17). Atoms only mirror non-sensitive auth flags (`isAuthenticatedAtom`, `currentUserIdAtom`).
- Inside React: `useAtom` / `useAtomValue` / `useSetAtom`.
- Outside React (in `mutationFn`, services): `getDefaultStore().get/set(atom)` only when arg-passing is infeasible.

**Naming**:
- Atom: `xxxAtom` suffix.
- Derived booleans: descriptive (`isAuthenticatedAtom`).
- Atom factories: `atomWith*`.

**Alternatives considered:**
- Nothing (TanStack + React Context only): sufficient for first 2–3 patient features, breaks down once 3+ contexts pile up.
- Zustand: slice-based, simpler but less granular. Both Jotai and Zustand are mainstream 2026 picks; Jotai wins on atomic composability and TS DX.
- Redux Toolkit: overkill at PoC scale.

### D17 — Session storage seam: **`expo-secure-store`**

Auth tokens (when patient login lands later) sit in the OS-managed encrypted keystore: iOS Keychain, Android Keystore. `expo-secure-store` is the official Expo wrapper.

Scaffold ships a thin abstraction at `src/lib/secureStorage.ts`:

```ts
import * as SecureStore from 'expo-secure-store';
import { Platform } from 'react-native';

export const secureStorage = {
  async get(key: string) {
    if (Platform.OS === 'web') return globalThis.localStorage?.getItem(key) ?? null;
    return SecureStore.getItemAsync(key);
  },
  async set(key: string, value: string) {
    if (Platform.OS === 'web') return globalThis.localStorage?.setItem(key, value);
    return SecureStore.setItemAsync(key, value);
  },
  async remove(key: string) {
    if (Platform.OS === 'web') return globalThis.localStorage?.removeItem(key);
    return SecureStore.deleteItemAsync(key);
  },
};
```

**Web caveat:** `expo-secure-store` has no web implementation. The shim falls back to `localStorage` on web. Web target is dev-only (D6), so the weaker guarantee is acceptable. When web ever becomes a shipping channel, this seam gets a stronger story (cookie-backed session, HTTP-only).

**Why now:** the wrapper is 20 lines and unblocks the login change without re-discussing storage. Cheap insurance against drift.

**Alternatives considered:**
- AsyncStorage: not encrypted; wrong for tokens.
- MMKV: faster, but adds a native dep we don't need at scaffold scale.
- Defer entirely: forces the login change to also pick a storage strategy, which is a second decision in one PR.

### D16 — MDR data boundary: **deferred to first feature change**

This scaffold ships no UI that displays data, so no MDR analysis is performed here. The outer envelope of what `digital-front-door` may render is **not declared** in this change. Each subsequent feature change MUST:

1. State explicitly what data its UI displays.
2. Re-run the MDR check from `openspec/changes/<change>/proposal.md`.
3. Add an entry to `openspec/mdr-watchlist.md` if any clinical interpretation, measurement display, or decision support is in scope.

**Why deferred:** PoC-tier features are still being discovered; locking the envelope now risks blocking exploratory work. Trade is the watchlist becomes the only enforcement point — see Risks.

## Risks / Trade-offs

- **Metro + pnpm symlink fragility** → Mitigation: `.npmrc` `node-linker=hoisted` + a moon `doctor` step that verifies the install before first `dev` run.
- **NativeWind class names diverge from web Tailwind** (RN doesn't support every utility; `gap-*` on older RN versions, `aspect-*`, etc.) → Mitigation: scope acceptance criteria to "lints + typechecks + boots on iOS / Android / web"; future feature changes carry their own visual acceptance.
- **`@rn-primitives` API churn** → Mitigation: pin minor versions; centralize wrapper layer so a bump is one PR.
- **MDR drift via feature creep** (heightened: D16 defers the data envelope) → Mitigation: proposal forbids clinical logic in this scaffold change; every future patient-facing feature change MUST run the MDR check and, if any clinical content lands, add a `mdr-watchlist.md` entry in the same PR. Review checklist enforces this.
- **Bundle / cold-start budget** on Android → Mitigation: not relevant at scaffold time; revisit when first feature lands.
- **Test runner divergence** from orchestrator (vitest vs `jest-expo`) → Mitigation: accepted; Expo's official runner is `jest-expo`. We document the difference in `apps/digital-front-door/AGENTS.md`.

## Migration Plan

This is greenfield — no migration. Rollback = `git revert` the change PR. The re-tier of patient surface in `openspec/scope.md` carries the highest signal; if we ever revert, those scope edits must be reverted in lockstep.

## Open Questions

- **Web target gating.** Do we ship the Expo web target as a first-class deliverable, or treat it as a dev convenience? Default to "dev convenience" until a delivery-channel decision lands (`BL-014`).
- **Backend prefix names a platform, not an audience.** `/mobile/*` works today because there is one mobile patient surface. If a desktop patient app or a second mobile surface appears, the prefix becomes ambiguous and a `/patient/*` rename (or layered `/patient/mobile/*`) becomes the right answer. Revisit when the second mobile-or-patient surface is proposed.
- **Linter pick.** Repo orchestrator uses ESLint today (verify). Decide whether `apps/digital-front-door` uses the same ESLint config (extending it) or Biome (lighter for RN). Default to ESLint to keep one tool in the repo.
- **Bundle ID at publish.** Scaffold uses `com.reaktor.zas.digitalfrontdoor` as a dev-only placeholder. Final iOS bundle identifier + Android package name are picked when an MVP publish-prep change wires EAS + store accounts. Changing the ID is destructive (re-signing, new store listing) — do not ship to production under this placeholder.
- **i18n bundle layout.** Per-feature locale files vs single `nl-BE.json`. Defer to first patient feature change; ship `nl-BE` skeleton only in this scaffold.
- **OpenAPI client.** Patient endpoints don't exist yet. Defer adding the generated client until the first patient feature change; scaffold ships a stubbed `src/lib/api.ts` placeholder.
