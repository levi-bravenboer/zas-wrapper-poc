Generate an alembic revision via the canonical moon task, then surface the file for review.

## Steps

1. Read the argument after `/new-migration` as the migration message. Validate it is:
   - non-empty
   - lowercase, present tense, action-first ("add patient identifiers", not "Patient identifiers added")
   - ≤72 chars
   If invalid, ask the user to rephrase before running anything.
2. Run `moon run backend:make-migration "<message>"`. This generates a revision in `apps/backend/alembic/versions/` against the current dev DB schema.
3. After it finishes, `ls -t apps/backend/alembic/versions/ | head -1` to find the new file, then `Read` it.
4. Review the autogenerated `upgrade()` / `downgrade()`. Flag anything alembic got wrong (dropped constraints, renamed-as-drop+add, missing indexes, server_default mismatches). Do not auto-apply fixes — show the user first.
5. Report: revision file path, summary of operations, and any flags from step 4.

## Notes

- Do not run `alembic revision` directly — moon sets the container, env, and working dir.
- Do not run `moon run backend:migrate` (apply) as part of this command. Migration application is a separate, explicit decision.
- If `make-migration` reports "no changes detected", the model and the DB are in sync — say so and stop.
