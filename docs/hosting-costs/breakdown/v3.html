The services we need — and why

Platform architecture after the MVP stack decisions (custom pathway engine instead of Temporal, Keycloak instead of Ory, native object storage instead of MinIO). Six components plus cross-cutting basics — that's the whole bill. Provider tabs show how each maps onto concrete services.

PostgreSQL database — highly available

scales with: patients in pathways · 5-yr rolling retention (75 GB → 350 GB → 2 TB)

Single relational store for everything operational: pathway state and scheduling for the custom engine, tasks, caregiver actions, the FHIR-aligned audit trail, Keycloak's identity data.

Why this way: Primary + synchronous standby in two zones (multi-AZ) with point-in-time recovery — backs the committed 99.9% SLA and the NIS2 continuity duty. Biggest single line at every tier.

Backend API

scales with: peak requests (sizing 100 → 150 → 300 req/s)

REST API for the caregiver orchestrator (SPA) and the patient app, plus server-sent events for live updates.

Why this way: SSE means long-lived connections — instances always-on (no scale-to-zero), raised LB idle timeouts. Two small replicas at MVP for zero-downtime deploys.

Background worker — custom pathway engine

scales with: open enrollments (8k → 23k → 110k concurrent)

Separate process for the engine's timers, polling and retries ('wound check due in 3 days'). Custom-built for MVP — the PoC's Temporal cluster was decided out.

Why this way: Isolated from the API so a burst of due tasks can't starve user requests. Same image, different entrypoint.

Keycloak — identity

scales with: identity count — effectively flat (one JVM container)

Login and accounts for caregivers and patients, brokering the Belgian eHealth OIDC instance as upstream IdP.

Why this way: Self-hosted on purpose: managed IdPs (Ory Network, Cognito, Entra External ID) bill per MAU — at 55k–155k MAU that fee dwarfs the one container it replaces. Authorization becomes app-level RBAC in the backend.

Object storage — attachments

scales with: ~10 MB per pathway patient (250 GB → 1.2 TB → 8 TB)

Wound photos and documents via presigned URLs, so files never stream through the backend.

Why this way: Native provider storage (S3 / Blob / GCS) in both shapes — 11-nines durability, lifecycle rules, ~€0.02/GB. PoC's MinIO stays dev-only.

Load balancer / reverse proxy

scales with: flat

TLS termination, host routing, serving the SPA, raised idle timeouts for SSE.

Why this way: Single-VM MVP does this with nginx on the box; from two app nodes (2030+) and in the managed shape it's the provider's LB.

Cross-cutting: monitoring, backups, registry, DNS, egress

scales with: egress scales with usage (250 GB → 750 GB → 3 TB/mo)

Provider-native logging/metrics/alerting (SLA + NIS2 incident duty), DB + storage backups, container registry, one DNS zone, internet egress.

Why this way: Small individually, always present — every matrix cell includes them so nothing hides.

Deliberately not on this bill

Video, messaging, questionnairesrun on Luscii's infrastructure (SDK reused as-is) — also why our credible SLA ceiling is Luscii's own 99.9%
Medical record storageHiX is the record of truth; the Belgian 30-year retention duty lives there. ZAS keeps ~5 years of operational data, so storage plateaus
Patient app hostingnative app via App Store / Play Store; no patient-facing web to host
Peopleon-call rota for 99.9%, ops time, NIS2 compliance work — salary money, likely exceeds this entire cloud bill
Vendor licences & auditsLuscii, ChipSoft/HiX, pen-tests, ISO 27001 / NEN 7510 certification

Assumptions & remaining unknowns

Load assumptions (derived, ±2× tolerated): peak 100/150/300 req/s sizing (sustained ~35/50/100) · DB 75 GB/350 GB/2 TB · attachments 250 GB/1.2 TB/8 TB (~10 MB per pathway patient) · egress 250/750/3000 GB/mo. Combined worst-case swing ≈ ±€500/mo at 2036 — inside the ±30% band. The expensive lines (HA database, always-on compute) hang off the confirmed projection numbers, not these estimates.
